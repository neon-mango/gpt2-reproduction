# Разбор предыдущей попытки: почему результат был хуже

Претендент: `prev-llm-attempt` (`/home/valeriy/custom-llm`) — GPT-1-подобная
модель (config "medium": 512 emb, 12 слоёв, 8 голов, vocab 16K, seq 256),
обученная на смеси wiki+QA (RU+EN). Цель текущего репозитория —
воспроизведение `openai-community/gpt2` (124M: 768 emb, 12 слоёв, 12 голов,
vocab 50 257, seq 1024, byte-level BPE, корпус WebText).

Кратко: модель прошлой попытки — это **не GPT-2** ни по данным, ни по
токенизатору, ни по архитектуре, ни по режиму обучения. Ниже по пунктам,
от самого важного к менее важному.

## 1. Данные — главная причина (на 2–3 порядка меньше и не та дистрибуция)

- GPT-2 обучался на **WebText: ~40GB текста, ~8M документов, ~9B токенов**
  (исходящие ссылки Reddit 3+ karma, вычищенный веб; Wikipedia исключена).
- В прошлой попытке: `ARCH_LIMITS` = 5k/50k/100k/200k документов на источник
  из набора wikipedia + alpaca + dolly + orca_math + no_robots + ru_saiga...
  Это **сотни МБ ≈ десятки М токенов** — в ~100–1000 раз меньше WebText.
- **Инструкционные датасеты не подходят для LM-воспроизведения.** Формат
  `Question:/Answer:` из alpaca/dolly/orca_math учит модель отвечать на QA, а
  не моделировать естественную веб-прозу. У GPT-2 задача другая: чистое
  next-token prediction на веб-тексте.
- **Смесь RU+EN** при маленьком бюджете дробит данные: на каждую языковую
  задачу остаётся ещё вдвое меньше. GPT-2 — англоязычная модель.
- **20–100 эпох** на малом корпусе: модель запоминает корпус, а не учит
  закономерности языка. Chinchilla-оптимум для их 75M — ~1.5B уникальных
  токенов, а не 30–100M токенов × 20 проходов.
- В новой версии: OpenWebText (открытая реконструкция WebText), 500k
  документов для первого прогона, полный корпус (~8M документов) докачивается
  той же командой; одна «эпоха», обучение по токенам, а не по эпохам.

## 2. Токенизатор: свой кодпоинт-BPE вместо byte-level GPT-2

- Свой BPE обучался на **том же маленьком корпусе** → словарь 8–16K
  кодпоинт-мерджей. GPT-2: 50 257 = 256 байтов + 50 000 мерджей, обученных на
  всём WebText, + regex-предтокенизация (запрет мерджей через границы
  букв/цифр/пунктуации).
- На английском веб-тексте старый словарь даёт **3.19 символа/токен против
  4.46** у GPT-2 — на 40% больше токенов на тот же текст (меньше полезного
  контекста, дороже вычисления).
- **Фатальный дефект устойчивости:** encode старого BPE **зацикливается**
  на символе, которого не было в обучающем корпусе (`i += best_len` при
  `best_len == 0`). На 1МБ реального веб-текста encode зависает и его
  приходится останавливать по таймауту. Byte-level GPT-2 кодирует любую
  строку байтов.
- Нет паритета с эталоном: со своим словарём веса gpt2 не загрузить и логиты
  не сверить — качество «воспроизведения» нечестно не измеряемо.
- Измерения и детали: [bpe-comparison.md](bpe-comparison.md).

## 3. Архитектура: 5 отличий от GPT-2 (`prev-llm-attempt/gpt.py`)

| Что | Прошлая попытка | GPT-2 (и новая версия) |
|---|---|---|
| Нормализация | post-LN (norm после residual, `gpt.py:168-174`), финального LN нет | pre-LN: LN перед attn/mlp + финальный `ln_f` (п. 2.3 статьи) |
| Активация | `nn.ReLU()` (`gpt.py:49`) | GELU (tanh-аппроксимация, `gelu_new`) |
| lm_head | отдельный `nn.Linear` (лишние параметры, ниже качество) | tying: `lm_head.weight = wte.weight` |
| Инициализация | дефолт PyTorch (kaiming-uniform у Linear) | N(0, 0.02), c_proj масштабируется 1/√(2·n_layer) (п. 2.3 статьи) |
| Контекст | 256 (отступление ради скорости) | 1024 |

Дефолтная инициализация + post-LN без warmup объясняют стартовый
`train_loss=10.79` в `deepseek/training.log` и медленную сходимость: у
глубоких (12 слоёв) трансформеров правильные init и pre-LN — не
косметика, а условие обучаемости.

## 4. Режим обучения

- **LR:** константные 2.5e-4, без warmup и без decay. GPT-2: warmup + cosine
  decay. Без clip градиентов (сами отметили в `deepseek/problems.md`).
- **Оптимизатор:** plain Adam без weight decay; сейчас стандарт — AdamW
  (wd 0.1 на матрицах, β2=0.95).
- **Эффективный батч:** 32 × accum 8 × 256 = **65K токенов/шаг** против
  512×1024 = **524K** в статье — в 8 раз меньше, при меньшем LR-диапазоне.
- **Датасет с перекрытием:** `GetData` (`gpt.py:176-196`) режет поток на окна
  с шагом 1: соседние примеры пересекаются на 255/256. «Эпоха» — это почти
  250-кратный показ тех же кусков, вычисления дублируются, а градиенты
  коррелируют. В новой версии — случайные окна на каждый шаг.
- **Чекпоинт без оптимизатора:** resume восстанавливал только веса; расписание
  (если бы оно было) стартовало бы заново. Теперь в `last.pt` лежат модель +
  оптимизатор + шаг + состояние ГПСЧ.

## 5. Оценка качества

- Качество мерилось «на глаз» по сэмплам. Не было: эталонной сверки
  архитектуры, стандартного val perplexity в стабильных условиях, генерации
  на фиксированном промпте в логе.
- В новой версии: `scripts/verify_parity.py` доказывает корректность
  архитектуры (логиты с эталонными весами **побитово** совпадают с HF gpt2),
  val_loss на детерминированных батчах + сэмпл на каждом eval.

## 6. Что в прошлой попытке было хорошо (перенесено)

- Атомарные чекпоинты (`.tmp` + `os.replace`), resume с проверкой битых файлов.
- Троттлинг `.item()`/логов раз в N шагов (не ломать CUDA-конвейер).
- `F.scaled_dot_product_attention` на CUDA, pin_memory + `non_blocking`.
- Аккуратное gradient accumulation (в DDP-варианте — `no_sync`).
- Серьёзная оптимизация BPE на C (индекс пар, linked-list мерджи) — по духу
  сохранена: теперь та же забота о throughput живёт в memmap-данных,
  возобновляемых шардах и fused AdamW.
- Тренировочный лог с таймстемпами.

## 7. Реалистичный бюджет на 3080 10GB (для понимания масштаба)

- ~30–50K токенов/с на 124M в bf16 → **Chinchilla-прогон ~2.5B токенов
  ≈ 1 сутки**; ~8B токенов (масштаб WebText для 124M) ≈ 2.5–4 дня.
- Прошлая попытка тратила сотни часов CPU на 30–100M токенов не тех данных —
  тот же бюджет на правильных данных уже даёт связный веб-текст.
